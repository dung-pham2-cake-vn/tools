Cake Lending — Tài liệu tích hợp cho đối tác

Tài liệu tổng quan mô tả toàn bộ bề mặt API giữa Cake by VPBank và đối tác cho các sản phẩm cho vay. Đọc file này trước, sau đó nhận spec OpenAPI riêng của sản phẩm (file index.yaml / PDF) từ Cake để biết chính xác field và example.

⚠️ Lưu ý bản quyền: Tài liệu thuộc bản quyền của Cake by VPBank. Mọi hình thức sao chép, chỉnh sửa, phát tán phải có đồng ý bằng văn bản.

Ai làm gì

BênTrách nhiệm
PartnerSở hữu khách hàng và giao diện. Gọi API Cake để mở hồ sơ, tra cứu, thu tiền. Expose các endpoint partner-* để nhận callback từ Cake. Giải ngân cho KH (nếu mô hình giải ngân qua ví đối tác).
CakeThẩm định, eKYC, phê duyệt hạn mức, sinh hợp đồng, hạch toán khoản vay, quản lý dư nợ, gửi callback trạng thái.

Bản đồ tài liệu

  1. Chọn mô hình tích hợp

    Native API hay Web (DOP webview) — §2. Quyết định này định hình toàn bộ phần còn lại.

  2. Chọn sản phẩm

    Cashloan / Payday / Paylater — §3. Dùng bộ lọc sản phẩm trên đầu trang để làm mờ phần không liên quan.

  3. Đi theo vòng đời khoản vay

    Đăng ký vay → Giải ngân → Tra cứu → Trả nợ / Tất toán. Riêng Paylater có thêm Thanh toán và Chuyển đổi trả góp.

  4. Đọc phần kỹ thuật dùng chung

    Signature, callback, môi trường, error code — §12–16. Bắt buộc với mọi mô hình.

  5. Tra chi tiết từng API

    §17 — header, request, response, error code của mọi endpoint, sinh tự động từ spec.

  6. Chạy checklist tích hợp

    §18 — thông tin cần trao đổi, test case và điều kiện go-live.

2. Hai mô hình tích hợp

5. Challenge — OTP / Facematch

Sub-flow dùng lại ở nhiều nơi. API chính trả về challenge_level + challenge_id; partner thực hiện đúng loại xác thực rồi gọi API confirm kèm challenge_id.

LevelLoạiPartner làm gìGặp ở
[1]NoneKhông gọi API challenge nào. Đi thẳng bước kế tiếp / API confirmmặc định ở check-profile; mọi luồng
[2]Facematch/challenge-facematch với ảnh selfietất toán, thanh toán
[3]SMS OTP/challenge-get-otp → /challenge-verify-otptất toán, thanh toán, trả góp
[4]DTN Cake OTPgiống [3], khác nguồn OTPchỉ ở check-profile, khi BRD yêu cầu
Quy tắc chung: luôn đọc challenge_level từ response rồi mới quyết định, không hard-code luồng OTP. Cùng một sản phẩm có thể đổi cấu hình challenge theo BRD mà không đổi API.
Giới hạn cần xử lý ở UI: OTP hết hiệu lực sau 2 phút (170002), sai 3 lần bị khoá 5 phút (170004), quá 6 lần/ngày khoá 24h (170005, 170006). challenge_id hết hạn trả 500027 — phải chạy lại từ API chính.

9. Thanh toán / Spending Paylater

Chỉ áp dụng cho Paylater. KH dùng hạn mức đã được cấp để thanh toán dịch vụ trên hệ sinh thái của đối tác; Cake ghi nợ vào khoản vay.

/get-installment-offers/payment-request /payment-confirm/payment-status /payment-revert/partner-payment-status
  1. (Tuỳ chọn) Lấy gói trả góp trước khi thanh toán

    /get-installment-offers trả danh sách kỳ hạn + phí để KH chọn trả góp ngay tại điểm bán.

  2. Tạo yêu cầu thanh toán

    /payment-request với service_code, payment_amount, partner_reference_id, installment_tenor (nếu trả góp). Trả order_id, payment_fee, challenge_level.

  3. Xác thực theo challenge_level

    Xem §5.

  4. Xác nhận

    /payment-confirm với order_id + challenge_id.

  5. Tra cứu / hoàn tiền

    /payment-status tra trạng thái; /payment-revert hoàn một phần hoặc toàn bộ. Cake callback /partner-payment-status khi trạng thái đổi.

Partner gọi API sinh webview thanh toán; KH xác nhận giao dịch và làm challenge (OTP / facematch) trong webview của Cake. Partner không gọi /payment-confirm, không gọi API challenge. Sau đó partner dùng các API cập nhật trạng thái để biết kết quả và đối soát.

12. Bảo mật & Signature

Áp dụng cho mọi request ở cả hai chiều, cả hai mô hình. Không có ngoại lệ.

Thuật toán ký

rawBody   = {{body}} + {{partner_key}}
hash      = sha256(rawBody)
signature = base64_encode(rsa.SignPKCS1v15(rand.Reader, privKey, crypto.SHA256, hash))

Partner tạo cặp khoá RSA 1024 bit: private key (PKCS#8) giữ bí mật, public key (X.509) gửi Cake.

Header theo chiều gọi

ChiềuHeader bắt buộcAi kýAi verify
Partner → CakeContent-Type, partner, signature Partner (private key partner)Cake (PARTNER_PUBLIC_KEY)
Cake → Partner (partner-*)Content-Type, signature — không có partner Cake (private key Cake)Partner (CAKE_PUBLIC_KEY)
Bắt buộc verify signature ở chiều callback. Endpoint partner-* nhận lệnh ghi nợ / giải ngân — không verify chữ ký nghĩa là bất kỳ ai biết URL đều gọi được.

Lớp bảo vệ khác

  • IP whitelist hai chiều — partner whitelist dải IP Cake, Cake whitelist IP partner (§14).
  • TLS — HTTPS bắt buộc, không hỗ trợ plain HTTP.
  • Partner ID — CAKE_PARTNER_ID ở header partner để Cake định danh đối tác.

13. Callback & Idempotency

Endpoint prefix partner- là Cake gọi vào hệ thống đối tác. Đối tác phải expose. Hợp đồng callback giống hệt nhau ở Native và DOP.

Hợp đồng response — cố định 3 field

Ngoại lệ duy nhất: /partner-disburse-status là endpoint truy vấn, trả thêm data.

Quy tắc idempotency: Cake retry khi timeout hoặc nhận code != 1. Partner phải khử trùng lặp theo khoá nghiệp vụ (loan_code với giải ngân, order_id với thanh toán) và trả cùng kết quả cho request lặp — không thực hiện lại hành động chuyển tiền.
Yêu cầu vận hành với endpoint callback: timeout xử lý ≤ 10s, trả HTTP 200 với body hợp lệ, không trả redirect, không yêu cầu auth bổ sung ngoài signature, và log lại để đối soát.

18. Checklist tích hợp

Giai đoạn 1 — Thống nhất phạm vi

  • Chọn sản phẩm: Cashloan / Payday / Paylater
  • Chọn mô hình: Native API hoặc Web (DOP)
  • Chốt mô hình giải ngân: partner callback hay external bank
  • Chốt phương thức trả nợ: VAN (QR), request→confirm, hoặc cả hai
  • Chốt các luồng tuỳ chọn: tất toán, thanh toán/spending, trả góp, collection reminder
  • Chốt cấu hình challenge theo BRD (mặc định [1] — không OTP ở pre-check)
  • Nhận spec OpenAPI riêng (index.yaml / PDF) từ Cake

Giai đoạn 2 — Phát triển

  • Implement ký signature và verify signature chiều callback
  • Expose đủ endpoint partner-* theo phạm vi đã chốt
  • Xử lý idempotency theo loan_code / order_id
  • Sinh partner_reference_id duy nhất mỗi giao dịch, lưu log kèm response_id
  • Đọc challenge_level từ response thay vì hard-code luồng OTP
  • Map toàn bộ error code sang thông báo cho KH (§16, §17)
  • Xử lý khung COB 23:50–04:00 ở UI

Giai đoạn 3 — SIT

  • Nhận credential SIT/UAT từ Cake: CAKE_PARTNER_ID, CAKE_PARTNER_KEY, CAKE_PUBLIC_KEY, CAKE_API_URL, product_id/group, dải IP Cake
  • Cung cấp cho Cake: PARTNER_API_URL, PARTNER_PUBLIC_KEY, dải IP partner, đầu mối kỹ thuật & vận hành
  • Whitelist IP hai chiều đã thông — gọi thử một API bất kỳ không bị chặn
  • Ký / verify signature chạy đúng ở cả hai chiều
  • Onboarding happy path đến LOAN_ACTIVE

Giai đoạn 4 — UAT

  • Các nhánh từ chối: reject pre-check, EKYC_REJECT (làm lại từ check-profile), loan reject
  • Hợp đồng: hết hạn, huỷ, sai OTP quá số lần Native
  • Giải ngân: thành công, thất bại, và retry trùng partner-disburse-request
  • Trả nợ: đủ trạng thái SUCCESS/FAILED/HOLD, chặn trùng partner_reference_id
  • Tất toán: is_terminable = false và happy path
  • Callback: partner trả code != 1 → xác nhận Cake retry đúng
  • Thanh toán + chuyển đổi trả góp Paylater
  • Collection reminder: phân trang hết cursor, gửi thông báo đúng channel
  • Đối soát cuối ngày khớp giữa hai hệ thống

Giai đoạn 5 — Go-live

  • Nhận bộ credential PROD (khác UAT)
  • Whitelist IP PROD hai chiều
  • Smoke test PROD với hồ sơ thật, hạn mức nhỏ
  • Thống nhất quy trình đối soát và kênh xử lý sự cố
  • Chốt SLA phản hồi endpoint callback và ngưỡng cảnh báo
